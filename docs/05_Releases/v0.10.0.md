# Overview

This release bundles the full Tier 4 vertical slice — Family and Membership — plus follow-on
work that landed on top of it: a dynamic relationship-graph feature for Family, a
children-stats aggregate endpoint for Organization, a shared frontend badge/config layer used
by all six verification UIs, a narrow ad-hoc data-fix migrations folder, a cross-module data
integrity test suite, and a rate-limiter test-isolation fix discovered while growing the
Membership test suite. All of it merged from a single feature branch,
`feature/tier4-family-membership`, into `develop` (merge commit `4842b20`).

**410 tests total** now cover the codebase: 21 (Tier 0 Bootstrap) + 59 (Tier 1 Foundation) + 72
(Tier 2 Organization, up from 64) + 61 (Tier 3 Person, up from 56) + 8 (security middleware) +
67 (Tier 4 Family) + 99 (Tier 4 Membership) + 23 (cross-module data integrity). One known failing
test, `test_kumari_transition_has_event` (SS5 seed still needs a `KUMARI_TRANSITION` journey
event — deferred, see `docs/PROJECT_DOCUMENTATION.md` → Deferred Items).

# Features Included

## 1. Tier 4 Family Module (DDL + API + Web UI)

`database/ddl/04_family/` — 5 tables: `family_group`, `family_relationship`,
`family_head_history`, `family_transition_history`, and `family_link` (a graph-edge table
storing direct `PARENT_OF`/`SPOUSE_OF` relationships only — see Family Graph below).

`api/routers/family.py` — 7 read-only endpoints under `/api/v1/family`: family group list with
filters + pagination, family group detail, family group members, family group head history,
plus 3 newer endpoints (`/graph`, `/sakha-alignment`, `/person/{pk}/membership-summary`).

`frontend/family.html` + `frontend/assets/js/family.js` — Family Verification UI, including a
family-tree visualization and Sakha-alignment mismatch badges.

67 new tests in `tests/test_family.py`, including `TestOrgAdminFamilyFilter` and
`TestSakhaAlignment` classes. **No test coverage yet for `/graph` or
`/person/{pk}/membership-summary`** — flagged as a pre-freeze gap, not fixed in this release.

## 2. Family Graph — Dynamic Relationship Computation

`api/services/family_graph.py` — a new architectural layer, distinct from `routers`/`schemas`.
BFS graph traversal over `nss.family_link` edges computes human-readable relationship labels
(e.g. "Father", "Spouse's Sister") relative to a `viewer_person_pk`, via a `PATH_LABELS` lookup
keyed by `Step` tuples. Powers `GET /api/v1/family/families/{pk}/graph?viewer_person_pk=`.

`GET /api/v1/family/families/{pk}/sakha-alignment` implements the FAM-036 majority-rule
"effective Sakha" computation — `is_aligned` is hardcoded `True` by design (the returned Sakha
is always the computed majority); per-member `is_home_sakha` flags surface real mismatches.
**This same majority-rule SQL is duplicated verbatim** in `organization.py`'s `/children-stats`
(see item 3) — not yet factored into a shared helper.

`GET /api/v1/family/person/{person_pk}/membership-summary` bridges family context to membership
context for a UI panel.

## 3. Tier 4 Membership Module (DDL + API + Web UI)

`database/ddl/05_membership/` — 12 tables: `sangha_sevi` plus status/renewal/transfer/
affiliation/journey/review history tables, and `parichaya_patra`/`anumati_patra` + their
history tables. Implements the three-tier member identity model frozen for Tier 4: Sangha Sevi
ID (permanent) / Local Sakha Number (Sakha-scoped, persistent across transfers) / Kendra Number
(annual, per FY).

`api/routers/membership.py` — 7 read-only endpoints under `/api/v1/membership`: member list with
filters + pagination, member detail, member Sakha affiliations, member Parichaya Patra records,
member journey events, 7-field member search (`sangha_sevi_id`, `person_id`,
`local_sakha_erp_id`, name trigram 0.45, mobile, email, Kendra number), and 4-field person search
(`person_id`, name trigram 0.45, mobile, email). Trigram email-split (`re.split(r'[.@]', q)[0]`)
prevents false-positive matches. Search auto-selects a single result; inline detail panel in
search tabs.

`frontend/membership.html` + `frontend/assets/js/membership.js` — Membership Verification UI.

99 new tests in `tests/test_membership.py`. **No test coverage yet for `/membership-summary`**
(shared gap with Family, item 1).

## 4. Organization `/children-stats` Endpoint (Tier 2 grows 6 → 7 endpoints)

`GET /api/v1/organization/organizations/{organization_pk}/children-stats` — aggregate
family/member/person counts per direct child, recursing through descendant Sakhas and applying
the same FAM-036 majority-rule "effective Sakha" computation Family's `/sakha-alignment`
implements independently. Its recursive CTE has **no depth-cap guard**, unlike `/hierarchy`'s
`depth < 10` guard — a circular parent reference could recurse indefinitely; flagged, not fixed,
in this release. The endpoint's own docstring claims it's used by the org-admin sidebar, but
`organization.html`/`organization.js` have no reference to it yet — also flagged, not wired up.

`tests/test_organization.py` grew from 64 to 72 tests, including a new `TestChildrenStats`
class.

## 5. Shared Frontend Badge/Config Layer

`frontend/assets/js/nss-config.js` (display-name overrides, e.g. `PROBATIONARY` → "Darshaka",
badge-class lookup maps, document-visibility rules) and `frontend/assets/css/badges.css` (every
`badge-status-*`/`badge-type-*`/`badge-aff-*`/`badge-gender-*` class) — extracted so all six
verification pages (`index.html`, `foundation.html`, `organization.html`, `person.html`,
`family.html`, `membership.html`) share one source of truth instead of redefining these classes
locally in inline `<style>` blocks.

## 6. Database Migrations Folder + Extended Seed/Integrity Tests

`database/migrations/` — a narrow escape valve for one-off ad-hoc data-fix scripts against
databases already bootstrapped with now-stale seed values (currently `update_darshaka.sql`,
fixing `PROBATIONARY`'s display name). Not a schema-migration framework; `02_build.sh` does not
run anything in this folder automatically.

`database/seed/99_extended_test_data.sql` / `99_fix_memberships.sql` — standalone,
manually-run verification-data scripts adding families F2/F3, persons P14–P17, and members
SS6–SS8 to exercise org-admin drill-down and Sakha-alignment mismatch badges (FAM-036/FAM-037).

`tests/test_data_integrity.py` — 23 new cross-module smoke tests checking every module has at
least one active entity, catching empty-table scenarios per-module tests might silently pass
through.

## 7. Rate-Limiter Test-Isolation Fix

slowapi's `Limiter` is a module-level singleton shared across the entire pytest process, not
scoped per test file. The reset fixture previously lived only in `tests/test_security.py`,
which reset it before that file's own tests but left every other file's requests accumulating
against the same 60/minute budget. Once Membership's test suite added dynamic seed-discovery
helpers that loop `GET /members` repeatedly, cumulative requests within a single pytest run
pushed the shared counter over the limit — surfacing as confusing, unrelated-looking failures
(`KeyError`/`TypeError` in `TestJourneyEvents`, a flat `429 == 200` in a security-header test).
Fixed by moving the reset to a global `autouse=True` fixture in `tests/conftest.py`.

## 8. Business Rule MBR-019C — Darshaka Stage Optional for Kishor/Kumari-Origin Members

Documented in `docs/03_Solution/modules/membership/04_membership_business_rules.md`: for
non-youth applicants, the Probationary/Darshaka stage (and its Anumati Patra) is mandatory
before promotion to Regular. For applicants with a Kishor Puja or Kumari Sangha background, the
Darshaka stage is optional, at the sanctioning Sangha President's discretion — such members may
be admitted directly to Regular with no Anumati Patra history at all. Surfaced by, and fixed
alongside, a fragile test assumption in
`test_regular_member_has_historical_expired_ap` (previously assumed every `REGULAR` member has
historical `EXPIRED` Anumati Patra; now searches across all `REGULAR` members, skip-guarded if
none qualify).

## 9. Documentation Reconciliation

`CLAUDE.md`, root `README.md`, and `docs/PROJECT_DOCUMENTATION.md` reconciled for all of the
above. `docs/03_Solution/api/API_CONTRACT.md` added (46 endpoints total, superseding
per-tier-only contract docs as the consolidated reference going forward, alongside the existing
`FOUNDATION_API_CONTRACT.md`/`ORGANIZATION_API_CONTRACT.md`/`PERSON_API_CONTRACT.md`). All 5
per-layer code-explanation docs updated with full Tier 4 Family/Membership, family-graph,
children-stats, and rate-limiter-fix coverage. Security audits gained
`docs/03_Solution/security/SECURITY_AUDIT_TIER0_4.md` and `TIER4_SECURITY_AUDIT.md`; the four
earlier per-tier audit docs moved from `code_explanations/` to a dedicated `security/` folder.

# Frozen Decisions (New in v0.10.0)

* **Three-tier member identity model** — Sangha Sevi ID (NSS-wide, permanent) on `sangha_sevi`;
  Local Sakha Number (per Sakha, per affiliation, persistent — archived on transfer, never
  reassigned, reactivated on return) on `membership_sakha_affiliation`; Kendra Number (annual,
  per FY) on `parichaya_patra.document_number`.
* **`family_link` stores only direct edges** (`PARENT_OF`/`SPOUSE_OF`) — all other relationship
  labels are computed dynamically via BFS traversal in `api/services/family_graph.py`, not
  stored.
* **Membership status vocabulary extends the unified `STATUS` category** (`RENEWAL_PENDING`,
  `ON_HOLD`, `DISCIPLINARY_REVIEW` added) rather than introducing a separate
  `MEMBERSHIP_STATUS` category.
* **Associate members never receive an Anumati Patra** (MBR-019B); **the Darshaka/Probationary
  stage is mandatory for non-youth applicants but discretionary for Kishor Puja/Kumari
  Sangha-origin applicants** (MBR-019C, new this release).
* **`api/services/` is now an established layer** for business logic too complex to inline in a
  router (starting with `family_graph.py`) — future non-trivial computed-response logic should
  follow this pattern rather than growing inside `routers/`.

# Notes

Unlike v0.9.0 (which bundled two separately-developed feature branches), this release is a
single feature branch — but the largest one yet by a wide margin (17 new tables, 15 new
endpoints, 202 new tests). The Family Graph and Organization children-stats features were
developed as follow-on work on top of the base Tier 4 slice rather than as separate branches,
consistent with the "tag promptly after each feature branch merges" lesson from v0.9.0's notes —
this is the first release since that lesson where only one branch needed bundling.
