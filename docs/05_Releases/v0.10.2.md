# Overview

Patch release fixing a Neon deploy failure: Phase 9 of `render_build.sh` (grant `nss_db_backend`
read-only access) errored with `role "nss_db_backend" does not exist`.

Root cause: `database/scripts/00_create_database.sql` normally creates both `nss_db_owner` and
`nss_db_backend`, but it requires a true PostgreSQL superuser connection plus `dblink` back to
`localhost` — meaningless on a managed Neon.dev connection — so it was never run there. Neon
deploys had no step that actually created either role before the grant step tried to use them.

Commit: `621ea52` — `fix(database): create nss_db_owner and nss_db_backend roles on Neon before
granting`.

---

# Fixes

`render_build.sh` now creates both `nss_db_owner` and `nss_db_backend` idempotently, right
before the grant step, matching local dev's role-naming convention (`nss_db_*` = PostgreSQL
infrastructure roles).

**Note carried into this release:** the running API on Render still connects as whatever
`DB_USER` is configured (the Neon-provided owner role used for the whole build), not as
`nss_db_backend` — this change prepares the roles for least-privilege enforcement without yet
turning it on in the actual deployment. Switching the API's runtime connection to
`nss_db_backend` on Render remains open.

---

# Database Objects Summary

No schema changes. Role creation only (`nss_db_owner`, `nss_db_backend` — both already existed
as a naming convention for local dev; this release makes Neon deploys create them too).
