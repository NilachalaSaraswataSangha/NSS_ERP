# Overview

This release bundles two pieces of work that landed on `develop` since v0.8.0 and had not yet
been tagged into `main`: a migration retiring Organization's dedicated
`organization_type_master`/`organization_status_master` tables in favor of Foundation's generic
`master_category`/`master_data` pattern, and the full Tier 3 Person vertical slice (DDL rewrite,
4-endpoint read-only API including pg_trgm fuzzy search, a 2-tab verification UI, and 56 new
integration tests). Person's own gender/marital-status/blood-group FKs follow the same
`master_data` pattern the Organization migration established, rather than dedicated per-domain
master tables — Foundation's `master_data` seed gained a new `BLOOD_GROUP` category (8 values)
to support this. Along the way, shared cursor→Pydantic and pagination-constant helpers were
extracted into a new `api/helpers.py`, consumed by both the new Person router and the refactored
Organization router (which also gained `limit`/`offset` pagination).

**208 tests total** now cover the codebase: 21 (Tier 0 Bootstrap) + 59 (Tier 1 Foundation) + 64
(Tier 2 Organization, up from 51) + 56 (Tier 3 Person) + 8 (security middleware).

# Features Included

## 1. Organization Master-Data Migration

Retires `organization_type_master` and `organization_status_master` and replaces them with rows
in Foundation's `master_data` table, matching the project's frozen "Master Data Driven"
principle:

* `master_category` gains an `ORGANIZATION_TYPE` category (10 values, including two new types —
  `PARIBARIK_ASANA`/`PARIBARIK_SANGHA` — not in the original 8-type set), and the former
  `MEMBERSHIP_STATUS` category is renamed/unified into a single `STATUS` category (13 values)
  shared across modules, replacing the per-module `ORGANIZATION_STATUS` split.
* `nss.organization`'s FK columns are renamed to `organization_type_master_data_pk` and
  `status_master_data_pk`, both referencing `nss.master_data`.
* `api/routers/organization.py`'s `/types` and `/statuses` endpoints (paths unchanged) now query
  `master_data` joined to `master_category` by `category_code`; `OrganizationStatusResponse` is
  renamed to `StatusResponse`, with status fields renamed `organization_status_*` → `status_*`
  throughout (type fields keep their `organization_type_*` naming).
* `id_sequence_master`'s padding-length CHECK constraint loosens from 4-12 to 2-12 digits to
  accommodate `PARIBARIK_SANGHA`'s 3-digit sequence; new seed sequences added for both new org
  types.
* `frontend/organization.html`/`organization.js` updated: field renames, 13 badge-status color
  classes (up from 6, covering the full unified status set).
* `database/scripts/{02_build,03_validate}.{sh,ps1}` and `render_build.sh` synced to the new
  phase/row counts.

## 2. FastAPI Tier 3 Person API (4 read-only endpoints)

Under `api/routers/person.py`, across both Person tables:

| Endpoint | Purpose |
|----------|---------|
| `GET /api/v1/person/persons` | List, optional `gender_code`/`marital_status_code`/`blood_group_code` filters, `limit`/`offset` pagination |
| `GET /api/v1/person/persons/{person_pk}` | Single person detail (full resolved context, masked Aadhaar) |
| `GET /api/v1/person/persons/{person_pk}/addresses` | All active addresses for a person (404 if person doesn't exist) |
| `GET /api/v1/person/search` | Trigram fuzzy search (`pg_trgm`) on name, plus `ILIKE` prefix match on `person_id`/`mobile_number` |

* List/detail endpoints resolve gender, marital status, blood group, and (detail only)
  emergency-contact relationship via `master_data` JOINs; addresses resolve address type plus
  the full city/postal-code/district/state/country geographic chain.
* **Aadhaar handling (PER-BR-081):** `aadhaar_encrypted` and `aadhaar_hash` are never returned by
  any endpoint or modelled in any Pydantic schema — only `aadhaar_last4` is exposed, for masked
  display.
* 3 new Pydantic response models (`api/schemas/person.py`): `PersonResponse`,
  `PersonSummaryResponse`, `PersonAddressResponse`.
* Full contract: `docs/03_Solution/api/PERSON_API_CONTRACT.md`.

## 3. Person DDL Rewrite — Foundation `master_data` Pattern

`database/ddl/03_person/02_person.sql` (`nss.person`, 28 columns) and `03_person_address.sql`
(`nss.person_address`) replace the earlier per-domain-master prototype
(`01_person_master_tables.sql`, now the only superseded file in the folder — its seed data lives
in Foundation's `master_data` seed going forward). DB-level format validation CHECK constraints
(mobile, email, country phone code, Aadhaar last-4, emergency phone) are included from day one
even though there's no write endpoint yet. Person has no seed data —
`database/scripts/03_validate.sh`/`.ps1` check table existence and zero row counts rather than
FK integrity against seeded rows.

## 4. Shared API Helpers (`api/helpers.py`)

Cursor→Pydantic conversion (`rows_to_models`, `row_to_model`) and pagination constants
(`DEFAULT_LIMIT = 100`, `MAX_LIMIT = 500`) extracted from per-router duplicates into a single
shared module, consumed by both `api/routers/person.py` (new) and `api/routers/organization.py`
(refactored). `api/routers/organization.py` also gained `limit`/`offset` pagination on
`/organizations` and `/hierarchy` as part of this same change.

## 5. Tier 3 Person Verification UI

* Served at `GET /person`, mirroring the existing `/foundation`/`/organization` pattern
* Nav bar now links all four verification UIs (`/`, `/foundation`, `/organization`, `/person`)

# Frozen Decisions (New in v0.9.0)

* **Organization's type/status classification lives in Foundation's `master_data`, not dedicated
  per-domain master tables** — `organization_type_master`/`organization_status_master` are
  retired; any future module classification should default to this pattern unless there's a
  specific reason to deviate.
* **`STATUS` is a single unified, cross-module lifecycle category (13 values)** — replacing what
  would otherwise have been separate `ORGANIZATION_STATUS`/`MEMBERSHIP_STATUS` categories; each
  module picks its applicable subset at the application layer rather than the DB layer.
* **Person's master-data FKs (gender, marital status, blood group, address type) resolve through
  the same `master_data` pattern** — the design docs' original per-domain-master proposal is
  superseded.
* **Aadhaar is never exposed beyond its last 4 digits, at every layer** — encrypted at rest in
  SQL, excluded from every SELECT the API issues, absent from every Pydantic response model, and
  never rendered in the UI. Any future write path must preserve this.
* **Shared cursor→Pydantic and pagination logic lives in `api/helpers.py`** — new routers should
  consume it rather than reimplementing `rows_to_models`/`row_to_model`/pagination bounds locally.

# Notes

Person is now the third Solution-layer module (after Foundation and Organization) with a
complete DB → API → UI vertical slice, verified end to end by its own test suite and a dedicated
security audit. Unlike Organization, Person ships with zero seed data — every test that needs an
actual row is skip-guarded, a pattern worth carrying into Tier 4 modules that also start without
seed data. The Organization master-data migration and the Person module were developed as
separate feature branches but had not yet been individually released before this cut — going
forward, prefer tagging a release promptly after each feature branch merges to `develop` rather
than letting multiple merges accumulate before the next tag.
