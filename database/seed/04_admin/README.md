# database/seed/04_admin/

Seeds the initial NSS Admin superuser account. Added in Tier 5 (released in v0.11.0). (Unrelated to `database/seed/04_family/` — the
shared `04_` prefix is coincidence; this folder has no `ddl/` counterpart.)

Authority: SOL-AUTH-006, Tier 5 decisions.

| File | Seeds |
|---|---|
| `01_admin_bootstrap.sql` (v2.0) | Person `P1` ("NSS Admin", gender `OTHER`), Sangha Sevi `SS1` (membership type `REGULAR`, status `ACTIVE`, attached to Kendra `KEN`, `is_system_account = TRUE` — the single reserved MBR-038A exception to the Sakha-only rule), `user_account` (`ACTIVE`, `force_password_change = FALSE`, 365-day expiry), `password_history` (`INITIAL`), `user_role` (`NSS_ERP_ADMIN`), `admin_scope` (`NSS-WIDE`, no organization) |

**Do not run this file directly with `psql`** — `user_account.password_hash` has no default and
the file contains a `%(password_hash)s` bind parameter that only exists at Python runtime (an
Argon2 hash generated by the app's own hasher). Run it via:

```bash
python3 scripts/bootstrap_admin.py
# or with a custom password:
python3 scripts/bootstrap_admin.py --password MyCustomPass1
```

The script reads this file and executes it as one multi-statement script in a single
transaction via `api/database.py::get_write_pool()` — so it needs `DB_WRITE_USER`/
`DB_WRITE_PASSWORD` (and the other `api/.env` DB settings) configured first, and the database
built through Phase 12 (Authentication + Administration DDL and the `nss_db_writer` grant).

Default login: `SS1` (or `P1`) / `Admin@123`. `force_password_change = FALSE`, so the first login
goes straight to `/dashboard` with no forced-change step. **Change this password before using
this seed against anything beyond a local dev DB.**

Run as Phase 13 of `database/scripts/02_build.sh`/`.ps1` and `render_build.sh`, after Phases 10–12.

**Idempotency — this is a clean-rebuild seed, not a reset tool.** Every INSERT is guarded by
`WHERE NOT EXISTS (...)`, so re-running never duplicates `P1`/`SS1` and **never overwrites an
existing password, lockout, or status** (the `user_account` INSERT is skipped if `P1` already
has an account — an earlier version of this README claimed a re-run resets the password; it does
not). The only `UPDATE`s are the two `GREATEST(current_value, 1)` counter advances on the
`PERSON` and `SANGHA_SEVI` `id_sequence_master` rows, which reserve `P1`/`SS1`. Version 2.0 also
dropped the old corrective `UPDATE` that forced `SS1` to `REGULAR`: membership type is now
selected explicitly by `value_code = 'REGULAR'` (an earlier draft picked the lowest
`display_order` type, which was `PROBATIONARY`/"Darshaka"), so a database seeded by that older
draft must be repaired by hand or rebuilt.

There are no `seed/06_authentication/` or `seed/07_administration/` folders — the authentication
and administration tables need no seed data beyond this bootstrap.
